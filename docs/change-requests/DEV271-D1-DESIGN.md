### Metrics and authorization

Use Dubai local dates converted to half-open timestamp ranges. Outbound call counts use `occurred_at`; corrections replace the original exactly once, while the append-only timeline remains intact. Resolve the latest valid correction per original call and test chains, branches and simultaneous corrections. Connected includes answered, callback requested, interested, not interested and declined. Blank rate for zero denominator. Count unique prospects for new interest (first qualifying event in period) and conversion (converted status and timestamp). The funnel uses the period-created cohort or selected batch, with each stage a subset of the preceding stage. Historical conversion without a recorded call remains visible in conversion totals and source quality. Follow-up completion is on time through due time plus one hour; overdue is open/in progress before now. Untouched requires not contacted status, no historical effective outbound call and no DNC. Targets sum effective daily targets across working dates.

Reuse the existing prospect SQL authorization boundary for all reads and exports. Agent scope is own, Manager team scope is active manager memberships, Director company-wide, Admin settings only. Resolve team/Agent/batch and drill-down IDs with scoped queries, return 404 for out-of-scope IDs and 403 for Admin content endpoints. Keep target/review writes scoped and owner-only call/note/interest writes. Audit reviews, policy changes, target changes, exports, snoozes and digest send/skip outcomes. Use current scope for dispatch and preview; never rely on a previously cached recipient team scope.

### Proposed review interpretations

- Treat missed scheduled retries as still due on later working days, below due callbacks; group and tie-break consistently. A callback-linked follow-up appears once at the higher follow-up priority.
- A timing recontact becomes eligible on the first working day of its selected month and only with no DNC, suppression, conversion or newer conflicting closure. Persist the due time for repeatable queue and reporting behavior.
- Keep historical `purchased_data` visible in unfiltered totals and expose it as an existing source in the filter. For cross-team reporting, allocate prospect events to the scoped prospect team and attribute call activity to its author. Define a single Agent row within each filtered view.
- Preserve original follow-up due time for discipline metrics. A snooze changes queue visibility, never the SLA due time. Review whether historical duplicate open tasks exist before considering a uniqueness constraint or reconciliation.

## Migration 172 design

| Object | Additions and invariants |
| --- | --- |
| `prospect_activities` | Nullable `next_step`, `not_interested_reason`, `not_interested_note`, `recontact_month`. Migration 172 adds no database-level next-step CHECK. The DEV271 call service enforces the required next step, allowed values and outcome combinations. Preserve append-only and suppression triggers. |
| `tasks` | Nullable FK `source_activity_id`, `snoozed_until`, `snooze_reason`; restrict these fields to prospect follow-ups and verify source activity belongs to the same prospect in the write path. Lock prospect first in every follow-up create or replace path; completion and replacement are atomic. Flag legacy duplicate tasks in preflight and exercise the handling in rehearsal. |
| `prospects` | Nullable purpose, budget band, property type, market, timeline, retry attempts, next retry time, parked time, last activity time and first-call due time. Treat missing retry state as zero attempts. Backfill only last activity from existing activity timestamps and first-call due time from created time under default Dubai working-day rules. Future writes maintain the values transactionally. |
| `prospect_preferred_areas`, `prospect_interest_history` | Prospect/area FK pair with unique key, and append-only history with actor, time and structured before/after snapshots, including area changes. |
| `prospect_cadence_policy_versions`, `prospect_agent_targets` | Versioned draft/active policy with one active version, valid weekday set and gap array, actors and approval timestamp. Effective-dated Agent target records with reason and actor; deterministic selection per day. |
| `prospect_override_reviews`, `prospect_digest_runs` | Review references exactly one activity or task, unique per source, with actor, timestamp and comment. ### R8 cPanel SMTP and Admin Email settings

Use authenticated cPanel SMTP with a separate sender mailbox and credentials from `lead@`. Use digest-specific configuration and secrets and leave `LEAD_EMAIL_*` settings out of this path. Confirm the cPanel SMTP hostname, port, TLS settings, exact sender address and reply handling. Ajit enters the mailbox password himself through the approved secret configuration interface. Never return it in settings responses or expose it in previews, logs, source or evidence.

Provide an Admin-only Email settings screen for the non-secret SMTP settings, sender and delivery status. Its Test Email action resolves the recipient from the signed-in Admin’s verified CRM email and accepts no recipient override. Enforce the CRM Test recipient allow-list at transport dispatch for every digest send, including scheduled sends, retries and the Admin test. Missing allow-list configuration fails closed. The Admin test remains subject to environment authorization and does not enable Production sending.

**Production enablement gate.** Keep `PROSPECT_DIGEST_EMAIL_ENABLED` off on Production. Verify the sender and send an approved synthetic digest from CRM Test to an allowlisted inbox. Capture SMTP acceptance and recipient-side evidence that the message reached the inbox, with SPF and DKIM pass, the expected sender, HTML and text, and no prospect contact details. Enable Production only after verification and Ajit’s separate approval. Keep in-app previews available while sending is off.

Use a durable claim and unique recipient/audience/date key. Schedule on the Dubai working-day calendar and enforce the confirmed hourly sending limit with throttling. Classify definite pre-DATA connection, TLS and authentication failures separately from ambiguous submissions. Retry a definite pre-DATA failure once after 30 minutes. Route an ambiguous submission to review with no automatic resend. Audit send, skip, retry and final outcome with safe error codes. Count failed Dubai delivery dates per address, one per day after retry exhaustion, and flag the address after three failed days for Admin review. Opt-outs, skipped non-working days and unresolved ambiguous submissions do not count as confirmed failures. Transport failure never blocks CRM requests.
